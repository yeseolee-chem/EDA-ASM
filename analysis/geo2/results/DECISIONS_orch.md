## A. 설계 (GEO1 `analysis/geo/r_launch.py` ONCE 방식 그대로 옮긴 것과 바꾼 것)
- **O-1 ONCE 전용** `g2_launch.py:1-33, 948-987`: r_launch의 `GEO_R_ONCE=1` 방식만 둔다(한 번 판단·제출 → `--begin=now+10minutes`로 자기 자신 재제출 → 종료). r_launch처럼 재제출이 실패하면 계산 노드 안에서 120 s마다 다시 시도하고(987), 46 h 동안 실패하면 exit 2. 상시 polling 모드(r_launch 기본)는 running slot을 계속 잡으므로 넣지 않았다.
- **O-2 chain 하나** `:953`(fcntl 비차단 lock `$GEO2/run_g2/launch.lock`; 잠겨 있으면 재제출 없이 종료 — lock을 가진 pass가 다음 pass를 낸다), `:609-614`(다른 `geo2_launch`가 PENDING이면 재제출하지 않음). 실수로 start 줄을 두 번 내도 다음 재제출 때 chain이 하나로 합쳐진다. lock이 파일 시스템에서 안 되면(EAGAIN/EACCES 외의 오류) lock 없이 진행한다(chain이 조용히 죽지 않게).
- **O-3 경로는 고정값** `:55-57`: `$GEO2`, `$GEO`, `$LAD`를 환경 변수에서 읽지 않는다. 작업 파일(`geo2.slurm`, `analysis/geo/jobs/*.slurm`, `d1_ladder/jobs/*.slurm`)이 같은 기본값을 export하므로 판정과 실행이 항상 같은 폴더를 본다(RUNBOOK_lad 0 "다른 값으로 export하지 않는다").
- **O-4 수동 job 인수(adopt)** `:688-694`: 작업 이름과 같은 job이 squeue에 있으면 그 job id를 state에 넣고 시도 1회로 센다. 이미 돌고 있는 Y job(`geo2_y_s0..2`, 결정 Y-1의 이름)을 그대로 이어받고, STOP 뒤 사람이 같은 `-J`로 다시 낸 job(예: accept 줄)도 판단한다.
- **O-5 MaxSubmit** `:64, 890`: 매 제출 전 `squeue -u $USER -h -r` 줄 수(배열 원소·다른 프로젝트·이 pass 포함)가 `MAX_SUBMIT - 1 = 19` 미만일 때만 낸다 → 제출 뒤 최대 19, 1칸은 다음 pass용(r_launch `MAX_SUBMIT - ONCE`와 같음). MaxJobs 10은 SLURM이 지킨다.
- **O-6 대기 상한을 자원 종류별로** `:64, 893`: r_launch R-lpt는 "자기 작업 PENDING ≤ 2"(전체)였다. GEO2는 GPU 작업(Y, C gpu, M3 4개)과 CPU 작업(H 5개, XGB)이 동시에 준비되는 구간이 있어, GPU 파티션이 붐빌 때 CPU 작업까지 막히지 않도록 cpu·gpu 각각 ≤ 2로 했다(최대 4개 대기). launcher가 running slot을 얻는 간격은 r_launch와 같은 이유로 짧게 유지된다.
- **O-7 손실 2회 = dead, scancel = STOP** `:64, 728`: r_launch처럼 marker 없이 끝난 job(충돌, exit 2, OOM, TIMEOUT, NODE_FAIL, sacct 기록 없음)은 한 번 다시 내고 두 번째 손실이면 dead(의존 작업 정지, STOP 파일). 단, r_launch와 달리 `CANCELLED`는 다시 내지 않고 STOP으로 둔다: scancel은 사람의 결정이고(사용자 규칙 "running job 취소 전 묻기"), launcher가 그것을 되돌리면 안 된다. 다시 돌리려면 `touch $GEO2/run_g2/retry/<task>`.
- **O-8 M3 재제출은 같은 GPU 종류** `:529, 586, 667`: train_atoms unit 지문에 GPU 이름이 들어가서 다른 종류에서 재개하면 첫 cached unit에서 exit 3이 된다(RUNBOOK_lad M-3). 직전 시도의 sacct AllocTRES(`gres/gpu:<type>=1`)에서 종류를 기록하고, 재제출 때 `--gres=gpu:<type>:1` + 그 종류가 있는 파티션만(`sinfo %P|%G`; 실패하면 5개 파티션 전부) 쓴다. retry 파일로 초기화해도 이 종류는 남긴다(`:643`).
- **O-9 오래된 보고서는 판정하지 않음** `:230-243`, 사용 `:520, 526, 534, 537, 539`: 같은 파일을 두 번 쓰는 단계(`R_check_geo2.json`: R-3과 collect 뒤 check)나 앞 단계 출력보다 먼저 쓰인 파일은 "newer_than"으로 걸러낸다(R-3 check는 `prereg_geo2.json`보다, 두 번째 check는 `L_report_geo.json`보다, `L_xgb_report_geo.json`은 10개 unit json보다, `E_report.json`·`E3_report.json`은 `L_predictions_geo.parquet`보다 새로워야 함).
- **O-10 쓰는 곳** `:151-159`: `$GEO2/run_g2/`(state, status, STATUS.txt, lock, HALT, retry/)와 `analysis/geo2/results/`(`STOP_<phase>.md`, `HPC_efficiency.csv`)만. 그 밖은 `STOP:`으로 종료.
- **O-11 GATE = commit + push 확인, launcher는 commit하지 않음** `:348-368`: 파일이 git에 tracked, HEAD 이후 변경 없음(train_atoms `gate_prereg_geo2`와 같은 규칙), 그 파일의 마지막 commit을 담은 remote-tracking branch가 있음(`git branch -r --contains`) = push됨. 명령서 1절 0-1("commit·push")과 8-3("학습 전에 commit·push")이 둘 다 push를 요구하므로 push까지 본다. `origin/<branch>`가 갱신되는 일반 `git push`를 전제로 한다.
- **O-12 git은 읽기만** `:171`: `GIT_OPTIONAL_LOCKS=0`으로 `git status/diff`가 index.lock을 잡지 않게 해서, 사람이 로그인 노드에서 commit하는 동안 충돌하지 않는다.

## C. 판정 규칙
- **O-25 판정 순서** `:686-740`: sticky done(한 번 done이면 state에 남음; 나중 파일 변경으로 되돌리지 않음) → squeue에 있으면 active(판정하지 않음: 도는 중인 보고서는 "running" 상태라 오판 위험) → done marker / 보고서 STOP → 의존 작업이 stop·dead·blocked이면 blocked → gate·check 대기 → 마지막 시도 결과. STOP은 sticky가 아니라 매 pass 다시 판정한다: 사람이 고치면(보고서를 치우고 retry, 또는 같은 이름으로 재제출) 다음 pass에서 이어진다. done이 STOP보다 먼저라, 사람이 accept 줄로 해결한 단계(예: `p --accept=F-1`)는 done이 되고 그 아래가 진행된다(위 단계의 STOP 파일은 기록으로 남음).
- **O-26 STOP 신호** `:202-205, 725`: exit 3(모든 역할 코드의 STOP 규약), 또는 0이 아닌 exit + 로그에 "STOP"으로 시작하는 줄(예: `eval_geo2.py`의 `SystemExit("STOP: ...")`는 exit 1). 보고서 json 키(`stop: true`, `verdict: fail`, `ok: false`, `status: fail`, `failed`)와 세 가지 예산(Y 30 GPU시간, H 2,500코어시간, smoke 80 GPU시간)도 STOP. 그 밖의 0이 아닌 끝은 손실(O-7).
- **O-27 M3 원자 작업의 done** `:97-99, 339-345, 722`: done = 그 작업의 unit json이 모두 있음 **또는** 마지막 시도가 COMPLETED exit 0(`train_atoms.py run`은 자기 unit을 모두 끝내야 0). 작업 k의 unit 목록은 `train_atoms.unit_list(3)[k::4]`의 정렬 규칙(MODEL_RANK GNN 0, AW 1, TF 2 → arm S, SH → fold)을 옮긴 것이고, selftest가 `train_atoms.py`의 `MODEL_RANK`/`ARMS` 줄과 (있으면) `$GEO2/regress/list_stage3.txt`와 비교한다(`:1018-1025`). 순서가 틀려도 exit 0 규칙과 collect(40 unit 확인)가 잡는다.
- **O-28 우선순위** `:881`: 준비된 작업은 (prio, DAG 순서)로 낸다. 0 = 다음 단계를 여는 짧은 작업(Y plan, Z, T, 보고서·merge·check, P, R, collect, E), 1 = H pilot, 2 = H 작업자, 3 = M3·XGB(긴 작업), 4 = Y, 5 = C part·E3 selftest, 6 = G·F slice. 긴 경로(H: pilot → 5 × 약 7 h)가 먼저 자리를 잡는다(r_launch R-lpt와 같은 취지).
- **O-29 sacct에 없는 job** `:669`: squeue에도 sacct에도 30분 넘게 없는 job은 UNKNOWN 종료로 보고 손실 처리(무한 대기 방지).
- **O-30 launcher 자체 오류** `:961-975`: pass가 예외로 죽으면 traceback을 담은 `results/STOP_LAUNCHER.md`를 쓰고 재제출하지 않는다(같은 버그로 10분마다 도는 것 방지). 이미 낸 작업은 그대로 돈다. 다음 정상 pass가 이 파일을 `.resolved_<time>`으로 바꾼다.

## D. 운영
- **O-31 제어 파일** `:60, 635-651, 869`: `$GEO2/run_g2/HALT`(제출·재제출 없음), `$GEO2/run_g2/retry/<task>`(그 작업의 시도 수·마지막 결과·sticky done을 지우고 다시 판정; 파일은 지움). 로그인 노드에서 `touch`/`rm`만으로 조작한다(JSON 손편집 불필요).
- **O-32 실행 파이썬** `:68, 606`: reactot python을 절대 경로로, conda activate 없이 실행(stdlib만 사용). 그래서 작업들은 start 줄을 낸 셸의 환경을 물려받는다 — 역할 runbook 줄을 로그인 셸에서 직접 친 것과 같은 환경. r_launch는 `conda activate reactot` 뒤 실행했지만, 그 활성화 환경이 FEAT·LADA wrapper에 섞이지 않게 바꿨다(각 wrapper는 자기 환경을 직접 켠다).
- **O-33 status·selftest** `:1046-1055`: 둘 다 읽기만 하고 SLURM job 안에서만 돈다(로그인 노드에서는 python 금지). orchestrator가 SLURM에서 코드를 시험할 때 쓰는 진입점이다: selftest = DAG 순서·이름·job 파일·script 경로·sbatch 줄 형식(`--time=48:00:00`, 로그 폴더, 파티션, GPU gres)·unit 순서·parser; status = 첫 pass가 무엇을 낼지(실제 sbatch 줄 출력).
